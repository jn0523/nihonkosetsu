# Git運用ポリシー（恒久ルール）

目的: Git運用ルールを実装計画書ではなく恒久ルールとして固定し、全エディタが常時参照できる状態にする。

## 1. 基本方針
- Git運用ルールは本ファイルを正本とし、個別の実装計画書に重複定義しない。
- 実装計画書では「本ポリシー参照」を記載し、差分が必要な場合のみ例外として追記する。

## 2. ブランチ運用
- **初期リリース前（プロトタイプ・MVP開発期）:**
  - 開発速度と仮説検証を最優先とするため、`main` ブランチを直接使って開発・コミットを進めて良い。
- **初期リリース後（本番運用期）:**
  - 本番品質と安定稼働を保護するため、`main` への直接コミットは禁止。
  - 日常の開発・修正作業は `feature/*` `bugfix/*` `hotfix/*` のいずれかで行う。
  - 本番へのリリース反映時は、必ず `release/*` ブランチを挟んで確定し、`main` への反映前にリリース前検査（`release_gate`）を実施する。

## 3. マージ・プッシュ前の確認（通常作業）
- 通常の `feature/*` / `bugfix/*` の作業・マージ時は、過剰なゲートを挟まず以下の軽量な確認を原則とする：
  - 変更概要とテスト結果（最低: 主要シナリオの再現確認）の記録。
  - シークレットや個人情報の混入がないことの確認。

## 4. release -> main 反映ルール (release_gate の限定適用)
- `ai-context/workflows/release_gate.md` は、**`release/*` から `main` への反映時のみ** 適用する（通常開発の `feature/*` コミットやPRには適用しない）。
- `release/*` から `main` へ push / merge する直前に、`ai-context/workflows/release_gate.md` を実行する。
- `release_gate` で `FAIL` が出た場合は反映不可。
- `CONDITIONAL` の場合は、条件・期限・担当者を確定してから反映可否を再判定する。

## 5. コミットメッセージ
- Conventional Commitsを推奨。
- 曖昧語（`update` `fix` `変更` `対応`）のみの説明は禁止。

## 6. 監査証跡
- 主要なマージ判断（PASS/CONDITIONAL/FAIL、例外承認、ロールバック判断）は記録を残す。
- 監査証跡は運用ドキュメントまたはリリース記録に紐づける。
